# Hosting an LLM on SageMaker AI

SageMaker AI lets you host your fine-tuned model as a **managed endpoint**: AWS runs the GPU machine, loads your model, and gives you a web address to send questions to. You don't log into a server or install anything — you describe what you want and AWS runs it. This is the main difference from [hosting on EC2%](1.2_EC2.md), where you manage the machine yourself.

This page only covers what is specific to SageMaker. Before you start, make sure you have done the shared AWS setup:

> **Prerequisites (all covered on other pages)**
> - Your model weights are in an S3 bucket.
> - You understand permissions/roles and have given your role read access to that bucket — see the permissions section on the [AWS overview page](1_AWS.md).
> - You have GPU instance quota, and you know which instance size your model needs — see the [AWS overview page](1_AWS.md).
> - You understand that a running endpoint is billed continuously while `InService` until you delete it — see the [intro page](index.md).

## Step 1 — Open SageMaker Studio and the notebook

In the AWS Console, search for **SageMaker AI** and open it. Open **Studio**, launch it, and create a **JupyterLab** space. Upload the deployment notebook (`FP_FT_Qwen2_5_AWS.ipynb`) and open it. Because the notebook runs inside AWS, it already knows who you are — you never type AWS keys into it.

Run the first cells to install the AWS library and connect. There is a helper cell defining a `wait_for_endpoint` function; run it as-is.

## Step 2 — The SageMaker execution role

Every SageMaker endpoint runs *as* a role called the **execution role**. This is the identity that will read your weights from S3, so it must have permission to do that. You set it near the top of the notebook by pasting its ARN, which you can find under **IAM% → Roles → (your SageMaker execution role) → Summary** in the Console.

> [!WARNING] The single most common SageMaker permissions mistake
> The default managed policy `AmazonSageMakerFullAccess` only grants S3 read access to buckets whose **name contains the word "sagemaker"**. If your weights live in a bucket with any other name, the endpoint will fail to start with a **403 / Access Denied** while downloading the weights. The fix is to attach a small inline policy giving the role read access to your specific bucket — the exact steps and the policy to paste are in the permissions section of the [AWS overview page](1_AWS.md). Do this before deploying.
>
> **You cannot fix permissions from inside the notebook.** The notebook runs as the execution role, and a role is deliberately not allowed to edit its own permissions. Any permission change has to be made by an account administrator from the IAM console. If you try it from the notebook you'll get an `iam:UpdateAssumeRolePolicy ... not authorized` error — this is expected, not a bug.

## Step 3 — Choose the container and point it at your weights

SageMaker serves your model using a ready-made **serving container%** that AWS provides. The notebook offers three (vLLM, SGLang, LMI).

You only need to edit a few values near the top of the notebook: the instance type (the GPU machine — pick it from the sizing table below; for our example 32B model this is `ml.g6e.12xlarge` with 4 GPUs), and the S3 location of your weights:

```python
instance = {"type": "ml.g6e.12xlarge", "num_gpu": 4}
model_data_s3 = "s3://your-bucket/your-model-folder/"   # must end with a slash
```

Then run the vLLM container cell as provided. Internally it tells the container to load the model from `/opt/ml/model` — the folder inside the machine where SageMaker automatically places whatever it downloads from your S3 location. You do not edit that path.

## Step 4 — Deploy

Run the three deployment cells in order. They register your model, describe the machine to run it on, and switch the endpoint on. The last cell waits and prints dots.

Expect this to take **several minutes** (often 10–15 for a large model): AWS rents the machine, downloads tens or hundreds of gigabytes of weights, and loads them onto the GPUs. When it prints `Status: 'InService'`, your model is live.

## Step 5 — Check status and read logs

You can check the endpoint's status at any time; the values are `Creating` (starting), `InService` (ready), and `Failed` (with a printed reason). SageMaker writes detailed container logs to **CloudWatch**, under the log group `/aws/sagemaker/Endpoints/<your-endpoint-name>`. Open the newest log stream there to watch the model load or to see the reason for a failure (for example, out-of-memory or an S3 permission error).

## Step 6 — Test it

The notebook has a simple "one question" cell and a streaming cell.

> [!WARNING] A single request must finish within 60 seconds.
> This is a hard SageMaker limit for real-time endpoints. A large model answering a long question can hit that wall and return a "timed out waiting for a response" error even though it is perfectly healthy. Always set a sensible `max_tokens` in the request. For genuinely long answers, use the **streaming** cell instead — streaming is not bound by the 60-second limit and shows the answer as it is generated.

## Step 7 — Cleanup (do this every time)

**Deleting the endpoint is the only thing that stops the hourly charge.** Run the cleanup cell, which deletes three separate objects: the endpoint, its configuration, and the registered model. Then run the listing cell to confirm nothing is left running.

Because switching an endpoint off and on is quick, the best habit is to delete it at the end of every session and simply re-run the deployment cells next time. If you ever lose track, the notebook includes a "delete everything" cell that clears all endpoints, configs, and models in the region.

## Choosing the right machine

The machine must have enough total GPU memory to hold your model plus working space for the conversation. As a rough guide for a standard 16-bit (fp16/bf16) fine-tune:

| Model size | Approx. weights | Suggested instance | GPUs | `num_gpu` |
|------------|-----------------|--------------------|------|-----------|
| 7B         | ~15 GB          | `ml.g6e.2xlarge`   | 1    | 1         |
| 14B        | ~28 GB          | `ml.g6e.2xlarge`   | 1    | 1         |
| 32B        | ~64 GB          | `ml.g6e.12xlarge`  | 4    | 4         |
| 72B        | ~145 GB         | `ml.g6e.48xlarge`  | 8    | 8         |

If you change the instance, update **both** `instance["type"]` and `instance["num_gpu"]` in Step 3. If a model is a tight fit and you see out-of-memory errors, lower `SM_VLLM_MAX_MODEL_LEN` in the container configuration cell (for example to `16384`), which reduces the working memory reserved for long conversations.

*(Note: See the [AWS overview page](1_AWS.md) for information on requesting GPU Quotas for these instances).*

## Troubleshooting

### The endpoint fails immediately with "Access Denied" reading S3
The execution role cannot read your bucket. Have an administrator grant the role `s3:GetObject` and `s3:ListBucket` on your specific bucket. See [Step 2](#step-2--the-sagemaker-execution-role).

### AccessDenied when editing a role from the notebook
If you try to change the role's permissions or trust policy *from inside the notebook*, you get an error like `iam:UpdateAssumeRolePolicy ... not authorized`. This is expected and correct — the notebook runs *as* the execution role, and a role is deliberately not allowed to edit its own permissions. Make any IAM change from an **administrator identity in the IAM console**, not from the notebook.

### A request "times out waiting for a response"
The endpoint is healthy, but a single answer took longer than the 60-second limit. Set a smaller `max_tokens`, or use the streaming method in the notebook, which is not bound by that limit.

### The model repeats itself or won't stop
The model isn't emitting its end-of-turn signal. Proper fix: check `generation_config.json` in your S3 folder — for a Qwen2.5 chat model the `eos_token_id` should include the `<|im_end|>` token (id `151645`). If your fine-tune saved only `<|endoftext|>`, correct the file in S3 and redeploy.

### The endpoint status is "Failed"
Read the CloudWatch logs (see [Step 5](#step-5--check-status-and-read-logs)). The two most common causes are out-of-memory (the machine is too small — see [Choosing the right machine](#choosing-the-right-machine)) or a problem reading the weights from S3 (permissions, or a wrong/misspelled `model_data_s3` path).

### It's been running a long time and I'm worried about cost
Run the listing check in the cleanup section of the notebook to see what is live, and delete anything you are not actively using. An endpoint bills for every second it is `InService`, used or not.
