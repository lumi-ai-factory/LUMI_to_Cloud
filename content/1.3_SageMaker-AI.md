# Hosting an LLM on SageMaker AI

SageMaker AI lets you host your fine-tuned model as a **managed endpoint**: you tell AWS which model, which serving container, and which machine to use, and it runs that machine, loads your model, and gives you a web address to send questions to. You never log into a server or keep one running. This is the main difference from [hosting on EC2%](1.2_EC2.md), where you run the same kind of serving container yourself on a machine you provision, secure, and keep alive.

The actual steps live in a notebook, `FP_FT_Qwen2.5_AWS.ipynb`, which you run cell by cell inside SageMaker. Each cell has a short note above it telling you what it does and what, if anything, to change. This page covers everything *around* that: the setup you need first, the traps that catch people, how to size the machine, and how to read failures.

Grab the notebook:

[FP_FT_Qwen2.5_AWS.ipynb](./assets/FP_FT_Qwen2.5_AWS.ipynb)

It is adapted from AWS's [SageMaker GenAI hosting examples](https://github.com/aws-samples/sagemaker-genai-hosting-examples). Those notebooks deploy the base, non-fine-tuned models; this one has been reworked to serve a Qwen2.5 fine-tune instead. If your own model is from a different family, take the matching example from that repo (GLM, Gemma, Kimi, and more) and adapt it for your fine-tune.

> **Prerequisites (all covered on other pages)**
> - Your model weights are in an S3 bucket.
> - You understand permissions and roles (see the [AWS overview page](1_AWS.md)).
> - You have GPU instance quota, and you know which instance size your model needs (see the [AWS overview page](1_AWS.md)).
> - You understand that a running endpoint is billed continuously while `InService` until you delete it (see the [intro page](index.md)).

## What you'll do in the notebook

In the AWS Console%, search for **SageMaker AI**, open **Studio**, launch it, and create a **JupyterLab** space. Upload `FP_FT_Qwen2.5_AWS.ipynb`, open it, and run the cells from top to bottom. Because the notebook runs inside AWS, it already knows who you are, so you never type AWS keys into it. Each cell has a short note above it explaining what it does; in order, they:

1. **Set up** the AWS library and connect.
2. **Set your execution role**, the identity the endpoint runs as.
3. **Point it at your weights** and **choose the machine** (instance type and GPU count).
4. **Deploy**, and wait until the endpoint is `InService`.
5. **Test it** with a single request or with streaming.
6. **Shut it down.**

The JupyterLab space itself runs on a small, cheap CPU instance, not a GPU: the GPU cost comes only from the endpoint you create in step 4. The rest of this page is the background for steps 2, 3, and 6, and what to do when something fails.

## The permissions trap (the most common failure)

Every SageMaker endpoint runs *as* a role called the **execution role**. This is the identity that reads your weights from S3, so it must have permission to do that.

The default managed policy `AmazonSageMakerFullAccess` only grants S3 read access to buckets whose **name contains the word "sagemaker"**, so if your weights live in a bucket with any other name, the endpoint fails to start with a **403 / Access Denied** while downloading them. Before deploying, grant the execution role read access to your bucket. An administrator does this from the IAM% Console:

1. Open **IAM → Roles** and click your execution role. *(Not sure which one? It is shown in your SageMaker domain's settings, and the notebook prints its name in step 2.)*
2. Click **Add permissions → Create inline policy**.
3. On the **JSON** tab, paste the policy below, replacing `YOUR-BUCKET` with your bucket name (in both places):

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ReadModelWeights",
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:ListBucket"],
      "Resource": [
        "arn:aws:s3:::YOUR-BUCKET",
        "arn:aws:s3:::YOUR-BUCKET/*"
      ]
    }
  ]
}
```

4. Click **Next**, name it (for example `read-model-weights`), and click **Create policy**.

`s3:ListBucket` on the bucket lets the role *see* what is in it; `s3:GetObject` on `YOUR-BUCKET/*` lets it *download* the files. To check what a role already has, open **IAM → Roles → (your role) → Permissions**; on a 403 this is the first place to look.

> [!WARNING] Don't try to fix this from the notebook
> The notebook runs as the execution role, and a role cannot edit its own permissions, so an attempt there fails with an `iam:UpdateAssumeRolePolicy ... not authorized` error. Make the change from an administrator identity in the IAM Console.

## The 60-second limit when testing

> [!WARNING] A single request must finish within 60 seconds.
> This is a hard SageMaker limit for real-time endpoints. A large model answering a long question can hit that wall and return a "timed out waiting for a response" error even though it is perfectly healthy. Always set a sensible `max_tokens` in the request. For genuinely long answers, use the **streaming** cell instead: streaming is not bound by the 60-second limit and shows the answer as it is generated.

## Reading status and logs

While the endpoint starts, its status moves from `Creating` to either `InService` (ready) or `Failed`. The notebook's status cells print this, and `describe_endpoint` prints a failure reason when there is one. For detail, SageMaker writes container logs to **CloudWatch**, under the log group `/aws/sagemaker/Endpoints/<your-endpoint-name>`. Open the newest log stream there to watch the model load, or to see why it failed (for example, out-of-memory or an S3 permission error).

## Cost: switch it off

**Deleting the endpoint is the only thing that stops its hourly charge.** An endpoint bills for every second it is `InService`, used or not. The notebook's cleanup cell deletes the three objects it created (the endpoint, its configuration, and the registered model); a listing cell then confirms nothing is left running.

Because switching an endpoint off and on is quick, the best habit is to delete it at the end of every session and re-run the deployment cells next time. The JupyterLab space the notebook runs in also bills (a small amount) while open, so stop that too, from the SageMaker Studio console, when you finish.

## Choosing the right machine

The machine must have enough total GPU memory to hold your model plus working space for the conversation. As a rough guide for a standard 16-bit (fp16/bf16) fine-tune:

| Model size | Approx. weights | Suggested instance | GPUs | `num_gpu` |
|------------|-----------------|--------------------|------|-----------|
| 7B         | ~15 GB          | `ml.g6e.2xlarge`   | 1    | 1         |
| 14B        | ~28 GB          | `ml.g6e.2xlarge`   | 1    | 1         |
| 32B        | ~64 GB          | `ml.g7e.2xlarge`   | 1    | 1         |
| 72B        | ~145 GB         | `ml.g6e.12xlarge`  | 2    | 2         |

If you change the instance, update **both** `instance["type"]` and `instance["num_gpu"]` in the notebook. If a model is a tight fit and you see out-of-memory errors, lower `SM_VLLM_MAX_MODEL_LEN` in the container cell (for example to `16384`), which reduces the working memory reserved for long conversations.

*(Note: See the [AWS overview page](1_AWS.md) for information on requesting GPU Quotas for these instances).*

## Troubleshooting

### The endpoint fails immediately with "Access Denied" reading S3
The execution role cannot read your bucket. Have an administrator grant the role `s3:GetObject` and `s3:ListBucket` on your specific bucket. See [the permissions trap](#the-permissions-trap-the-most-common-failure).

### AccessDenied when editing a role from the notebook
If you try to change the role's permissions or trust policy *from inside the notebook*, you get an error like `iam:UpdateAssumeRolePolicy ... not authorized`. This is expected and correct. The notebook runs *as* the execution role, and a role is deliberately not allowed to edit its own permissions. Make any IAM change from an **administrator identity in the IAM console**, not from the notebook.

### A request "times out waiting for a response"
The endpoint is healthy, but a single answer took longer than the 60-second limit. Set a smaller `max_tokens`, or use the streaming method in the notebook, which is not bound by that limit.

### The model repeats itself or won't stop
The model isn't emitting its end-of-turn signal. Proper fix: check `generation_config.json` in your S3 folder: for a Qwen2.5 chat model the `eos_token_id` should include the `<|im_end|>` token (id `151645`). If your fine-tune saved only `<|endoftext|>`, correct the file in S3 and redeploy.

### The endpoint status is "Failed"
Read the CloudWatch logs (see [Reading status and logs](#reading-status-and-logs)). The two most common causes are out-of-memory (the machine is too small; see [Choosing the right machine](#choosing-the-right-machine)) or a problem reading the weights from S3 (permissions, or a wrong/misspelled `model_data_s3` path).

### It's been running a long time and I'm worried about cost
Run the listing check in the cleanup section of the notebook to see what is live, and delete anything you are not actively using. An endpoint bills for every second it is `InService`, used or not.
