# Hosting an LLM on SageMaker AI

SageMaker AI lets you host your fine-tuned model as a **managed endpoint**: you tell AWS which model, which serving container, and which compute instance to use, and it runs that instance, loads your model, and gives you a web address to send prompts to. You never log into a server or keep one running. This is the main difference from [hosting on EC2%](1.2_EC2.md), where you run the same container, but on a machine you provision, secure, and keep alive.

The actual steps live in a notebook, `FP_FT_Qwen2.5_AWS.ipynb`, which you run cell by cell inside SageMaker. Each cell has a short note above it telling you what it does and what, if anything, to change. This page covers everything *around* that: the setup you need first, the traps that catch people, how to size the machine, and how to read failures.

### Grab the notebook

[FP_FT_Qwen2.5_AWS.ipynb](./assets/FP_FT_Qwen2.5_AWS.ipynb)

It is adapted from AWS's [SageMaker GenAI hosting examples](https://github.com/aws-samples/sagemaker-genai-hosting-examples). Those notebooks deploy the base, non-fine-tuned models; this one has been trimmed and reworked to serve a Qwen2.5 fine-tune instead. If your own model is from a different family, take the matching example from that repo (GLM, Gemma, Kimi, and more) and adapt it for your fine-tune.

### Download our Qwen 2.5 weights (full-parameter fine-tuned)

If you just want to run the notebook without making any changes, you can use our pre-fine-tuned Qwen2.5 model. The weights are publicly available on LUMI-O.

You will need to copy them from LUMI-O to your own AWS S3 bucket first. You can do this by using `rclone` (see [Moving data to AWS](1.1_Move_data.md) for how to set up the `AWS:` remote) to copy them directly between LUMI-O and AWS S3:

```bash
rclone sync lumi-462000131-public:lumi-to-cloud-fine-tuned-llm-voitanta/Qwen2.5_FP_FT AWS:BUCKET_NAME/Qwen2.5_FP_FT -P
```

- `lumi-462000131-public:...`: the public LUMI-O remote and path containing our fine-tuned weights.
- `AWS:`: the remote name you chose in `rclone config` (we suggested `AWS`), followed by a colon. It is case-sensitive.
- `BUCKET_NAME/Qwen2.5_FP_FT`: your AWS S3 bucket, then the folder to create inside it for this model.
- `-P`: show live transfer progress.

Once they are in your S3 bucket, point the notebook to that location.

### Prerequisites
- Your model weights are in an S3 bucket.
- You understand permissions and roles (see the [AWS overview page](1_AWS.md)).
- You have GPU instance quota, and you know which instance size your model needs (see the [AWS overview page](1_AWS.md)). To follow this notebook you'll need access to 1x `ml.g6e.12xlarge`.
- You understand that a running endpoint is billed continuously while `InService` until you delete it (see the [intro page](index.md)).

> [!TIP] Backup instances (Capacity issues)
> Newer instance types like the `g6e` are highly sought after. If your endpoint fails to create with an `InsufficientInstanceCapacity` error, AWS is temporarily out of stock of that hardware in your region. 
> 
> A very reliable fallback is the older (but plentiful) `g5` family. For a 32B model, use **`ml.g5.12xlarge`** (which has 4 GPUs and 96GB VRAM) instead.

## What you'll do in the notebook

In the AWS Console%, search for **SageMaker AI**, click **Open Studio**, create a **JupyterLab** space and run it (may take a minute or two). Click **Open JupyterLab**. Upload `FP_FT_Qwen2.5_AWS.ipynb` using the **Upload files** button, open it, and run the cells from top to bottom. Because the notebook runs inside AWS, it already knows who you are, so you never type AWS keys into it. Each cell has a short note above it explaining what it does; in order, they:

1. **Set up** the AWS library and connect.
2. **Set your execution role**, the identity the endpoint runs as.
3. **Point it at your weights** and **choose the machine** (instance type and GPU count).
4. **Deploy**, and wait until the endpoint is `InService`.
5. **Test it** with a single request or with streaming.
6. **Shut it down.**

The JupyterLab space itself runs on a small, cheap CPU instance, not a GPU: the GPU cost comes only from the endpoint you create in step 4. The rest of this page is the background for steps 2, 3, and 6, and what to do when something fails.

## Choosing the right machine

The machine must have enough total GPU memory to hold your model plus working space for the conversation. As a rough guide for a standard 16-bit (fp16/bf16) fine-tune:

| Model size | Approx. weights | Suggested instance | GPUs | `num_gpu` |
|------------|-----------------|--------------------|------|-----------|
| 7B         | ~15 GB          | `ml.g6e.2xlarge`   | 1    | 1         |
| 14B        | ~28 GB          | `ml.g6e.2xlarge`   | 1    | 1         |
| 32B        | ~64 GB          | `ml.g6e.12xlarge`  | 4    | 4         |
| 72B        | ~145 GB         | `ml.g6e.48xlarge`  | 8    | 8         |

If you change the instance, update **both** `instance["type"]` and `instance["num_gpu"]` in the notebook.


*(Note: See the [AWS overview page](1_AWS.md) for information on requesting GPU Quotas for these instances).*

## Cost: switch it off

**Deleting the endpoint is the only thing that stops its hourly charge.** An endpoint bills for every second it is `InService`, used or not. The notebook's cleanup cell deletes the endpoint, its configuration, and the registered model object (this is just metadata, your actual model weights safely remain in S3).

**Remember to stop the notebook space too.** The JupyterLab space the notebook runs in also bills (a small amount) while open. The final cell in the notebook contains a script to automatically shut down the JupyterLab space when you finish, or you can stop it manually from the SageMaker Studio console.
